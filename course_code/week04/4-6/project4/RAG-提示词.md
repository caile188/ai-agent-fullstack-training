# 提示词：为 project3 Codebase Agent 增加「查询外部 RAG」的工具 rag_query

---

## 角色

你是 `project3/v2` 这个**受治理 Codebase Agent** 的维护者。项目由三块构成：
pi 扩展点（`src/pi/*`）、工具运行时（`src/runtime.ts` + `src/registry.ts` + `src/policy.ts` + `src/contract.ts`）、
以及十件仓库工具（`src/tools/*`）。这些工具都要过治理层：注册进 `ToolRegistry`、受 `PolicyEngine` 的
RBAC 与白名单约束、启动时经 `verifyContracts` 自检、调用时落审计。

## 目标

给这个 Agent 增加一件**只读工具 `rag_query`**：让它能查询外部 RAG 知识库（BGE 向量 + BM25 关键词混合检索），
**同时返回「答案」和「引用来源追溯」**——即每条结论对应的来源文件、章节标题、相似度分数与证据片段，
编号与答案里的 `[n]` 引用一一对应，方便追溯出处、杜绝凭空编造。

验收：**模型调用 `rag_query {question}`，拿回一段答案 + 一份带编号的来源清单，编号能对上。**

## 必须交付的事

### 能力边界

- 新增一件工具，语义为：自然语言问题 → RAG 检索 → 返回「答案 + 带编号的来源追溯」。
- 只读：不得改动 RAG 知识库、不得写工作区文件、不得触发人工确认。
- 检索能力来自外部调用 `4-6/rag/query.py`（机器可读输出模式）；工具本身不得重新实现检索/生成逻辑。
- 工具对模型暴露的身份必须稳定为 `rag_query`（白名单、审计、脚本、自检都按这个名字对齐）。

### 输入契约（模型能发什么、发错了怎样）

- `question` 必填且为非空自然语言问题。**仅含空白字符的问题必须在真正发起检索之前被拦下**（否则白跑一轮检索 + 一次 LLM 调用）。
- 可选参数必须各有明确取值域与默认值，越界即拒：
  - `mode`：`hybrid` / `vector` / `bm25`，默认 `hybrid`。
  - `top_k`：整数 1–20，默认取配置的 top_k。
  - `doc_type`：`doc` / `code` / `web` / `table` / `pdf`，缺省 = 不按类型过滤。
  - `no_llm`：布尔，缺省 `false`；为真时只检索、不调 LLM。
- 参数对象必须严格：除上述字段外的任何字段一律拒绝，不得把无意义参数带进子进程。

### 输出契约

- 正常返回必须**同时**含「答案」与「来源追溯」两块；来源逐条带 编号 / 文件 / 标题 / 分数 / 证据摘要。
- **来源编号与答案里的 `[n]` 必须严格一一对应**——这是可追溯性的硬要求，编号错位即判不合格。
- 当 `no_llm` 为真、或 LLM 不可用时：答案可以缺省，但来源追溯必须照常完整返回，并说明答案为何缺失。
- 底层返回的不是合法结构时：不得假装成功，必须转成明确错误，并附足以定位问题的诊断（如 stderr 末尾）。

### 治理与自检不变量（违背则要么跑不起来、要么直接判失败）

- 工具必须走完整治理链路：注册 → 受 RBAC 与白名单约束 → 经工具运行时执行并落审计 → 启动时通过契约自检。任一环缺失都不可接受，不得绕过。
- 权限边界：读权限 `rag:read`，须授予 `reviewer` / `developer` / `maintainer` 三个角色；模型侧可见须进 `codebase-agent` 白名单。
- 契约自检要求「每条规则 ↔ 每个已注册工具」双向成立。因此本工具必须**无条件注册**：不得按开关条件注册（关闭态若"有规则无工具"会让启动自检直接失败）。开关关闭时的正确表现是「调用时给出明确的未启用错误」，而不是「工具不存在」。
- 超时边界：工具的整体超时**必须严格大于**内部子进程超时，给进程留出收尾余量；否则外层 deadline 会先杀掉一次本可成功的调用。
- 进程调用边界：工作目录被固定在沙箱工作区根，而 RAG 目录在其之外——调用必须靠与 cwd 无关的绝对脚本路径达成，不得依赖切换工作目录。

### 配置必须能表达这几件事

- 一个启用开关；RAG 根目录（相对配置目录解析，最终须落在 `4-6/rag`）；python 解释器；子进程超时；默认 top_k。
- 缺省安全：完全不写这一段时，工具仍在、但不启用，且不破坏改造前的既有行为。

### 运行环境边界（不进代码，但必须成立）

- `python` 必须指向装齐 RAG 依赖的解释器。
- LLM 依赖 `~/.hermes/.env` 里的 MiniMax key；取不到时检索与引用照常返回，仅答案为空并说明原因。
- RAG 必须先入库，否则底层返回带 `error` 的结果。

## 约束

- 不破坏现有单测；`npm test` 必须全绿（当前基线 126）。
- 保持现有代码风格：中文注释、错误码大写下划线、每个参数都写 `description` 与边界。
- 工具必须走 `ToolRuntime`，照常落审计、照常受 RBAC/白名单约束，不许绕过治理层。
- 运行前 RAG 必须先入库（`python ingest.py` 生成 `storage/`），否则 `query.py` 返回带 `error` 的 JSON。

## 验收清单

1. `npm run check` 通过，`npm test` 全绿。
2. `python 4-6/rag/query.py -q "会话的有效期是多少分钟？" --json --top-k 3` 输出单行合法 JSON，
   `answer` 带 `[n]` 引用，`citations[]` 含 `file/heading/score/snippet` 且 `index` 对齐。
3. 用真实 `config/platform.yaml` 起 `rag_query` handler：
   - `hybrid` + LLM：返回答案 + 引用追溯；
   - `no_llm` + `bm25`：不出答案但**仍给完整引用追溯**。
4. `rag.dir` 解析为 `4-6/rag` 且存在，`query.py` 存在。

## 测试命令

```bash
# 0) RAG 先入库（首次或改语料后）
cd 4-6/rag && python ingest.py --overwrite

# 1) RAG 侧接口自测
python query.py -q "会话的有效期是多少分钟？" --json --top-k 3
python query.py -q "登录会话有效期" --json --mode bm25 --top-k 2 --no-llm

# 2) Agent 侧类型检查与全量单测
cd 4-6/project3/v2 && npm run check && npm test
```
